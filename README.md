# 📰 AI 뉴스 요약 자동화 프로젝트

> RSS로 수집한 뉴스 데이터를 자동으로 가져와, Gemini AI로 핵심 내용을 요약한 뒤 Notion 데이터베이스에 저장하는 자동화 시스템입니다.  
> Make(Integromat)를 활용해 **뉴스 수집 → 중복 검사 → AI 요약 → Notion 저장**까지의 전 과정을 하나의 시나리오로 구성했습니다.

---

## 1. 프로젝트 개요

본 프로젝트는 매일 발행되는 방대한 뉴스 중 **관심 주제 기사만 자동으로 선별·요약·아카이빙**하기 위해 설계되었습니다.  
사람이 직접 뉴스를 검색·요약하는 반복 작업을 자동화하여 **시간 절감**과 **정보 관리 효율화**를 목표로 합니다.

---

## 2. 프로젝트 목표

- ✅ 관심 키워드 기반 뉴스 자동 수집
- ✅ 중복 뉴스 저장 방지
- ✅ AI를 활용한 뉴스 요약 자동 생성
- ✅ Notion을 활용한 뉴스 아카이빙 자동화

---

## 3. 사용 도구

| 도구 | 용도 |
|------|------|
| **Make** | 자동화 시나리오 구성 |
| **Google Gemini API** | 기사 요약 생성 |
| **Notion Database** | 결과 저장 및 관리 |
| **Google News RSS** | 뉴스 원본 데이터 수집 |

---

## 4. 자동화 흐름

전체 시나리오는 다음과 같은 순서로 동작합니다.

1. **매일 오후 1시**, RSS에서 뉴스 기사 수집
2. **주제 필터링** — 관심 키워드 포함 기사만 선별
3. Notion 데이터베이스에서 동일한 원문 링크가 이미 존재하는지 검색 (중복 검사)
4. 중복이 아니면 Gemini API를 호출하여 기사 요약 생성
5. 제목·요약·원문 링크·발행일을 Notion에 저장
6. 오류 발생 시 Retry 정책에 따라 재시도

### 시나리오 구조

```
[RSS] → [주제 필터] → [Notion 검색(중복확인)] → [Gemini 요약] → [Notion 저장] → [Retry 핸들러]
```

> 💡 **설계 포인트:** 중복 기사를 **Gemini 호출 이전**에 걸러내어, 불필요한 API 호출을 방지하고 **비용과 처리 시간을 절감**하도록 설계했습니다.

---

## 5. Notion 데이터베이스 구성

본 프로젝트에서는 아래 5개의 속성을 사용했습니다.

| 속성명 | 타입 | 설명 |
|--------|------|------|
| 제목 | Title | 뉴스 기사 제목 |
| 요약 | Text | Gemini가 생성한 요약문 |
| 원문링크 | URL | 뉴스 원문 주소 |
| 발행일 | Date | 기사 발행일 |
| 작동 시간 | Date | Make 시나리오가 작동한 시간 |

---

## 6. 워크플로우 상세

### 6-1. RSS 뉴스 수집

RSS 모듈을 통해 지정한 피드에서 최신 기사를 자동으로 가져오도록 설정했습니다.  
필요 이상의 뉴스가 수집되는 것을 막기 위해 **최대 5개**의 뉴스를 수집하도록 제한했습니다.

- **RSS 링크:** Google News RSS (`https://news.google.com/rss/search?q=...`)
- **선정 이유:** 네이버 등 일부 포털은 RSS를 지원하지 않아, 가장 보편적으로 넓은 범위를 커버할 수 있는 **Google News RSS**를 선택했습니다.

#### 📌 스케줄 트리거 동작 원리 *(신규 보완)*

RSS 수집은 **Make의 스케줄 트리거(Schedule)** 를 기반으로 동작합니다.

- **동작 방식:** Make는 내부적으로 **크론(Cron) 표현식**과 유사한 스케줄러를 사용해, 정해진 시각에 시나리오를 자동 실행합니다.
- **설정값:** `매일 오후 1시(13:00)` 1회 실행
  - 예시 크론 표현식: `0 13 * * *` (매일 13시 0분 실행)
- **선정 이유:** 대부분의 주요 기사가 오전~오후 시간대에 발행되므로, **오후 1시**에 실행하여 당일 오전 기사까지 안정적으로 수집하도록 설계했습니다.
- **동작 원리:** 트리거가 발동되면 → RSS 피드에 요청 → 신규 항목(최대 5건)을 순차적으로(Bundle) 다음 모듈로 전달합니다.

---

### 6-2. 주제 필터링 *(단계 명확화 — 신규 보완)*

수집된 뉴스 중 **관심 주제와 관련된 기사만** 통과시키기 위한 필터링 단계입니다.

Make의 **Filter** 기능을 사용하여 기사 **제목(Title)** 에 지정한 키워드가 포함된 경우에만 다음 단계로 진행하도록 구성했습니다.

#### 🔑 필터링 키워드 목록

본 프로젝트는 **AI·기술 트렌드**를 주제로 하므로, 아래 키워드를 기준으로 필터링합니다.

| 분류 | 키워드 |
|------|--------|
| 핵심 | `AI`, `인공지능`, `머신러닝`, `딥러닝` |
| 데이터 | `데이터`, `빅데이터`, `데이터분석` |
| 응용 기술 | `챗봇`, `생성형AI`, `LLM`, `자동화` |

- **필터 조건:** `Title` **Contains** `AI` (OR 규칙으로 키워드 확장 적용)
- **설계 이유:** 빠르게 변화하는 기술 트렌드를 효율적으로 파악하기 위해, 관련 핵심 키워드를 중심으로 필터 목록을 구성했습니다.

> 💡 **개선 참고:** 대소문자 및 단어 일부 매칭 오류를 방지하려면, 필요 시 정규식(Regex) 또는 정확 매칭 조건을 추가할 수 있습니다.

---

### 6-3. 중복 필터링

Notion의 **Search Objects** 모듈을 사용하여, 이미 저장된 기사와 원문링크(URL)가 동일한 경우 저장하지 않도록 구성했습니다.

- **중복 기준:** 원문링크(URL)
- **목적:** 동일 기사 반복 저장 방지
- **필터 조건:** `원문 링크(URL)` **Contains** `{{URL}}`

---

### 6-4. AI 요약 호출

Gemini API를 활용하여 수집한 뉴스 기사 내용을 자동으로 요약하도록 구성했습니다.

#### 🤖 프롬프트 설계 기준 *(신규 보완)*

**사용 프롬프트:**
```
이 기사의 내용을 3줄로 요약해줘

제목: {{Title}}
원문 링크: {{URL}}
본문: {{Description}}
```

| 설계 요소 | 기준 및 이유 |
|-----------|--------------|
| **입력 데이터** | RSS의 `Description`(본문 요약)을 핵심 입력으로 사용. URL은 원문 확인용으로 함께 전달 |
| **3줄 제한 방식** | 프롬프트에 `"3줄로 요약"` 지시문을 명시하여 출력 길이를 제어 |
| **3줄로 제한한 이유** | 한눈에 파악 가능한 분량으로, 사용자가 **긴 글을 읽지 않고도 핵심을 즉시 이해**할 수 있도록 함 |
| **원문 링크 병기** | 3줄 요약만으로 부족할 경우, 링크를 통해 **전문 확인이 가능**하도록 보완 |

> 💡 요약은 `Description` 기반으로 생성되므로, RSS가 제공하는 본문 정보의 범위 내에서 요약이 이루어집니다.

---

### 6-5. Notion 자동 저장

중복이 아닌 기사에 대해서만 **제목·요약·원문링크·발행일**을 Notion 데이터베이스에 자동 저장하도록 구현했습니다.

- **Connection:** Notion Internal Integration 연결
- **저장 필드:** 제목(Title), 요약(Text), 원문링크(URL), 발행일(Date), 작동 시간(Date)

---

## 7. 에러 처리 정책

자동화 과정에서 외부 API 또는 네트워크 문제로 일시적인 오류가 발생할 수 있으므로, 아래와 같은 에러 처리 정책을 적용했습니다.

### 적용한 정책

- **Retry 에러 핸들러 사용**
- 재시도 횟수: **2회**
- 재시도 간격: **5분**

### ⚙️ Retry 설계 이유 및 후속 처리 *(신규 보완)*

| 항목 | 내용 |
|------|------|
| **Retry 적용 이유** | Gemini API·Notion API 호출 시 발생하는 **일시적 네트워크 오류 / 서버 응답 지연**에 대응하여 자동화의 **안정성**을 확보하기 위함 |
| **재시도 횟수(2회)** | 일시적 오류는 대부분 짧은 시간 내 복구되므로, 과도한 재시도로 인한 지연을 막기 위해 2회로 제한 |
| **재시도 간격(5분)** | 서버 부하·네트워크 문제가 해소될 시간을 고려하여 5분으로 설정 |

#### 재시도 이후 후속 처리 방식

1. **성공 시:** 정상적으로 다음 모듈로 진행
2. **2회 재시도 모두 실패 시:**
   - 해당 Bundle은 **Incomplete Executions(미완료 실행)** 로 저장되어 **스킵(Skip)** 처리
   - 이후 관리자가 Make 대시보드에서 **수동 검토 및 재실행** 가능
   - (확장 가능) 실패 시 **이메일/Slack 알림**을 추가로 연결하여 즉시 인지 가능하도록 구성 가능

> 💡 이 정책을 통해 **일부 기사 처리 실패가 전체 시나리오 중단으로 이어지지 않도록** 설계했습니다.
